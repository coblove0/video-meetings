## Цель документа

Проверить технологические решения, заложенные в план, сверить их с текущими best practices (2026 год) для NestJS/Prisma/Next.js-стека этого репозитория, и дать конкретные рекомендации по реализации — конфигурация multer, безопасность загрузки, стриминг скачивания, прогресс-бар на фронтенде. Документ не меняет фазы плана, а детализирует «как» внутри уже согласованных задач.

## 1. Хранение файлов: локальный диск vs объектное хранилище

План (Фаза 1) закладывает хранение на диске сервера (`storagePath` в модели `MeetingFile`). Это осознанный компромисс для текущего масштаба проекта:

- В репозитории нет S3-совместимого сервиса, `docker-compose.yml` или очереди — добавление объектного хранилища (S3/GCS/MinIO) означало бы новый внешний сервис, который сейчас не нужен (см. `CLAUDE.md` § Database — в проекте уже принят паттерн «используй то, что реально развёрнуто локально»).
- Диск + Postgres — минимальный набор зависимостей, согласованный с духом остального репозитория (nest+prisma+pg, без лишней инфраструктуры).

**Рекомендация:** оставить локальный диск, но не хардкодить путь — вынести директорию хранения в `UPLOAD_DIR` (env, аналогично `DATABASE_URL`/`JWT_SECRET` в `apps/api/.env`), по умолчанию что-то вроде `./uploads` относительно `apps/api`. Директорию **обязательно добавить в `.gitignore`** (сейчас там нет записи под uploads) и создавать её при старте, если отсутствует.

Важно: если сервис в будущем будет разворачиваться в контейнере/на нескольких инстансах, локальный диск не переживёт рестарт/масштабирование — это стоит явно отметить как известное ограничение MVP (то есть `storagePath` как отдельное поле в БД, а не просто `filename`, — это правильная развязка: при переходе на S3 туда просто попадёт ключ объекта вместо пути на диске, схема БД не меняется).

## 2. Prisma-модель `MeetingFile`

План уже определяет поля (`originalName`, `size`, `mimeType`, `storagePath`, `createdAt`, `meetingId` FK). Дополнения, которые стоит учесть при написании миграции:

```prisma
model MeetingFile {
  id           String   @id @default(uuid())
  originalName String
  size         Int
  mimeType     String
  storagePath  String
  createdAt    DateTime @default(now())
  meetingId    String
  meeting      Meeting  @relation(fields: [meetingId], references: [id], onDelete: Cascade)

  @@index([meetingId])
}
```

- `onDelete: Cascade` на FK — если встреча когда-нибудь будет удаляться, записи файлов не должны оставаться сиротами в БД (сам файл на диске каскад не удалит — это отдельный вопрос жизненного цикла, но вне рамок этого плана, т.к. удаления встреч пока нет в API).
- `@@index([meetingId])` — список файлов всегда фильтруется по `meetingId`, индекс нужен уже на объёме в сотни записей.
- `size Int` достаточно (до ~2 ГБ), `BigInt` избыточен при разумном лимите размера файла (см. §3).
- В `Meeting` нужно добавить обратную связь `files MeetingFile[]`.
- Название модели `MeetingFile` — по аналогии с существующими `User`/`Meeting`, единственное число, PascalCase — соответствует конвенции схемы.

## 3. Backend: модуль и multer-конфигурация

### Структура модуля

Следовать паттерну `MeetingsModule`/`AuthModule` (CQRS, `impl/`+`handlers/`, contoller делегирует в `CommandBus`/`QueryBus`, а не сервису напрямую) — это явно прописано в плане и совпадает с архитектурой `apps/api/CLAUDE.md`.

Нюанс интеграции CQRS с multer: `FileInterceptor` — это Nest-интерцептор уровня контроллера, он ничего не знает про `CommandBus`. Правильное разделение ответственности:

1. `FileInterceptor('file', multerOptions)` на уровне контроллера отвечает **только** за приём multipart-запроса, лимит размера и запись файла на диск (или в память — см. ниже) через `diskStorage`.
2. Контроллер собирает `UploadMeetingFileCommand` из `@UploadedFile()` (даёт `Express.Multer.File` — путь на диске, оригинальное имя, mimetype, размер) и `@CurrentUser()`, и уже это диспатчит в `CommandBus`.
3. Хендлер команды делает `findFirst({ where: { id: meetingId, ownerId } })` (как в `GetMeetingHandler`) — если не найдено, **обязательно удалить уже записанный на диск файл** (`fs.unlink`) перед тем, как бросить `NotFoundException`, иначе файл-сирота останется на диске без записи в БД. Это единственное место, где multer и владение пересекаются: multer сохраняет файл _до_ проверки владения, потому что Nest выполняет интерцептор раньше тела метода контроллера.

Альтернатива — `memoryStorage()` вместо `diskStorage()`, чтобы держать буфер в памяти и писать на диск только после проверки владения в хендлере. При установленном лимите размера файла (см. ниже) и ожидаемом уровне нагрузки (учебный/внутренний проект) это безопаснее с точки зрения гигиены (нет файлов-сирот), но дороже по памяти на конкурентных загрузках. **Рекомендация:** для этого проекта — `diskStorage()` с очисткой файла-сироты в catch-ветке хендлера; это ближе к тому, что уже написано в плане («сохранение файла на диск» как отдельный шаг), и не требует держать файл целиком в памяти процесса.

### Валидация размера и типа

```ts
MulterModule.register({
  storage: diskStorage({
    destination: uploadDir,
    filename: (_req, file, cb) => {
      const ext = extname(file.originalname); // только для расширения на диске — не доверять как проверке типа
      cb(null, `${randomUUID()}${ext}`);
    },
  }),
  limits: { fileSize: MAX_FILE_SIZE_BYTES, files: 1 },
  fileFilter: (_req, file, cb) => {
    cb(null, ALLOWED_MIME_TYPES.includes(file.mimetype));
  },
});
```

Ключевые моменты (см. также §4 «Безопасность»):

- **Имя файла на диске генерируется сервером** (`randomUUID()` + расширение), а не берётся из `file.originalname`. Оригинальное имя сохраняется только как метаданные в БД (`originalName`) для отображения и `Content-Disposition` при скачивании. Это закрывает path traversal и коллизии имён одним и тем же решением.
- `fileFilter` по `file.mimetype` — это **только первый фильтр**, основанный на заголовке `Content-Type`, который целиком контролирует клиент и который ничего не доказывает (OWASP File Upload Cheat Sheet: доверять `Content-Type` от клиента эквивалентно доверять самозаявленному типу атакующего). Он нужен, чтобы быстро отбрасывать явно неподходящие запросы до записи на диск, но не является гарантией.
- **Более сильная проверка — по сигнатуре файла (magic bytes)**, после того как файл уже записан (или в памяти): прочитать первые байты и сверить с ожидаемой сигнатурой для заявленного MIME-типа (для этого есть библиотеки уровня `file-type`, либо ручная проверка нескольких байт для узкого allowlist типов проекта). Если PRD ограничивает список типов небольшим набором (документы/изображения), стоит добавить эту проверку в Фазу 1 как часть валидации, а не как отдельную будущую задачу — расхождение «заявленный MIME vs реальное содержимое» дешево проверить и дорого не проверить.
- `limits.fileSize` в multer — это защита от DoS ещё на уровне парсинга multipart, до `fileFilter` и до логики хендлера; без него нет верхней границы вообще (это явно отмечается как частая ошибка в свежих гайдах по NestJS-загрузкам). Значение лимита и allowlist типов стоит вынести в env (`MAX_FILE_SIZE_BYTES`, `ALLOWED_MIME_TYPES`), а не хардкодить — PRD может уточнять конкретные цифры, но конфигурируемость нужна независимо от значений.
- `@types/multer` сейчас не установлен как явная dev-зависимость (сам `multer@2.2.0` в дереве есть транзитивно через `@nestjs/platform-express`) — типы `Express.Multer.File` нужны, чтобы `@UploadedFile()` типизировался корректно; стоит добавить `@types/multer` в `apps/api/package.json` devDependencies при реализации Фазы 1.

## 4. Безопасность — сводный чеклист (OWASP File Upload Cheat Sheet)

Применительно к задачам плана:

| Риск                                                        | Где закрывается в плане                   | Как реализовать                                                                                                                                                                                                                  |
| ----------------------------------------------------------- | ----------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Path traversal через имя файла                              | Фаза 1, multer `filename`                 | Генерировать имя на диске (UUID), никогда не использовать `originalName` как часть пути                                                                                                                                          |
| DoS через размер файла                                      | Фаза 1, «лимит размера файла»             | `multer.limits.fileSize`, отдаётся понятная ошибка до записи на диск                                                                                                                                                             |
| Загрузка исполняемого/опасного контента под чужим MIME      | Фаза 1, «allowlist MIME-типов»            | `fileFilter` по заголовку + проверка магических байт после сохранения (см. §3)                                                                                                                                                   |
| Доступ к чужим файлам (IDOR)                                | Фаза 1 и 2, «проверка владельца»          | Единообразный `findFirst({ id: meetingId, ownerId })` во всех пяти ручках (upload/list/download/delete), 404 а не 403 — не палить существование чужой встречи, тот же паттерн, что уже применён в `GetMeetingHandler`            |
| Файлы, отдаваемые напрямую из webroot                       | — (не в плане явно)                       | Директория загрузок не должна быть статически смонтирована Express'ом (`app.useStaticAssets` и т.п.) — единственный путь получить файл обязан быть через `GET /meetings/:id/files/:fileId/download` с проверкой владения         |
| Рассинхронизация БД/диска при удалении                      | Фаза 2, «удаление записи и файла с диска» | Удалять сначала запись в БД, затем файл с диска (или наоборот — но обрабатывать `ENOENT` не как ошибку 500, а тихо игнорировать: если файла физически уже нет, конечный результат для пользователя всё равно «файла больше нет») |
| Утечка через `Content-Disposition` при нестандартных именах | Фаза 2, скачивание                        | См. §5 — кириллица/спецсимволы в оригинальном имени требуют RFC 5987-кодирования, иначе браузер либо обрежет имя, либо заголовок сломается                                                                                       |

## 5. Скачивание файла (Фаза 2)

NestJS предлагает `StreamableFile` как основной механизм для отдачи файлов потоком без буферизации целиком в памяти:

```ts
@Get(':fileId/download')
async download(...): Promise<StreamableFile> {
  const meetingFile = await ...; // findFirst с проверкой ownerId, иначе NotFoundException
  const stream = createReadStream(meetingFile.storagePath);
  return new StreamableFile(stream, {
    type: meetingFile.mimeType,
    disposition: `attachment; filename="${asciiFallback}"; filename*=UTF-8''${encodeURIComponent(meetingFile.originalName)}`,
  });
}
```

Важный нюанс для этого проекта: интерфейс на русском языке, значит оригинальные имена загруженных файлов почти наверняка будут содержать кириллицу. Простой `filename="${originalName}"` в `Content-Disposition` для не-ASCII имён либо некорректен по RFC 6266, либо браузеры трактуют его непредсказуемо. Нужна пара `filename` (ASCII fallback/транслитерация или просто "file") + `filename*=UTF-8''<percent-encoded>` — это стандартный паттерн (RFC 5987), который стоит сразу заложить в задачу Фазы 2, а не находить как баг после первого файла с русским именем.

`StreamableFile` требует либо возвращать его напрямую из метода контроллера (тогда Nest сам выставляет заголовки и управляет `Content-Length`), либо, если нужен полный контроль над заголовками через `@Res()`, — помечать `@Res({ passthrough: true })`, иначе ответ зависнет (частая ошибка, отмеченная в нескольких актуальных гайдах). Для этой задачи проще без `@Res()` вообще — вернуть `StreamableFile` с опциями `type`/`disposition`, как в примере выше.

## 6. Frontend (Фаза 3–4)

### Список и скачивание файлов (Фаза 3)

Скачивание с Bearer-токеном нельзя сделать через простую ссылку `<a href>` (браузер не добавит заголовок Authorization) — нужно делать `fetch` с заголовком, получать `blob`, и через `URL.createObjectURL` + временный `<a>` с `download` инициировать сохранение. Это стандартный паттерн для API, защищённых Bearer-токеном (в проекте нет httpOnly cookie — см. `apps/web/CLAUDE.md` § Auth, токен только в `localStorage`), и его стоит явно учитывать при оценке задачи «добавить скачивание файла» в Фазе 3.

### Загрузка с прогресс-баром (Фаза 4)

План требует «индикатор процесса загрузки». Здесь есть значимая техническая развилка:

- **`fetch` + `FormData`** — простой и современный API, но **не даёт события прогресса аплоада** ни в одном стабильно поддерживаемом виде: `fetch` не эмитит upload-progress events, а вариант с `ReadableStream`+`duplex: 'half'` в теле запроса пока не одинаково поддержан во всех браузерах (Chrome — да, Firefox/Safari — нет по актуальным данным), и авторы рекомендуют не полагаться на него для progress UI.
- **`XMLHttpRequest`** — единственный API с надёжным `xhr.upload.onprogress` во всех браузерах уже много лет; это по-прежнему стандартная рекомендация именно для progress bar на 2026 год, несмотря на то что XHR формально «legacy» API.

**Рекомендация:** для Фазы 4 использовать `XMLHttpRequest` (или лёгкую обёртку над ним) именно для запроса загрузки файла, а не `fetch`, который используется в остальном фронтенде (`register`/`login`/`page.tsx`). Это единственное место в приложении, где потребуется XHR вместо fetch — стоит явно задокументировать это решение в `apps/web/CLAUDE.md`, когда до него дойдёт реализация, чтобы не выглядело непоследовательным выбором.

Выбор файла и кнопка — HeroUI: `apps/web/CLAUDE.md` требует получать актуальную документацию компонентов через `.agents/skills/heroui-react/scripts/get_component_docs.mjs` перед использованием (нативный `<input type="file">` можно стилизовать под HeroUI, если готового File-компонента нет — это стоит проверить через тот же скрипт в момент реализации Фазы 4, а не полагаться на память о HeroUI v2).

## 7. Тестирование

- **Backend e2e** (Фаза 1–2, `supertest`): загрузка файла в e2e-тесте делается через `.attach('file', Buffer.from(...), 'name.txt')` — не нужен реальный файл на диске тестового окружения, буфер в памяти достаточен. После теста стоит подчищать `UPLOAD_DIR` (или использовать отдельную тестовую директорию через env), чтобы прогоны e2e не копили файлы на диске разработчика.
- **Frontend e2e** (Фаза 3–4, Playwright): `page.setInputFiles()` — стандартный способ подать файл в `<input type="file">` без реального диалога ОС; для теста ошибки валидации достаточно захардкодить фикстуру нужного размера/типа в `apps/web/test/fixtures` (или сгенерировать буфер на лету).

## 8. Итоговые рекомендации по фазам плана

Все пункты ниже — уточнения внутри уже существующих задач плана, без изменения структуры фаз:

1. **Фаза 1:** добавить `@types/multer` в `apps/api/package.json`; вынести `UPLOAD_DIR`/`MAX_FILE_SIZE_BYTES`/`ALLOWED_MIME_TYPES` в `.env`/`.env.example`; генерировать имя файла на диске через `randomUUID()`, не доверять `originalname`; добавить проверку по магическим байтам в дополнение к `fileFilter` по MIME; обрабатывать файл-сироту при отказе по владению (удалять с диска, если `findFirst` не нашёл встречу).
2. **Фаза 2:** использовать `StreamableFile` с явным `type`/`disposition`, включая RFC 5987-кодирование `filename*` для кириллических имён; при удалении не падать 500 на `ENOENT`, если файла на диске уже нет.
3. **Фаза 3:** скачивание через `fetch` → `blob` → `URL.createObjectURL` (Bearer-токен нельзя передать через `<a href>`).
4. **Фаза 4:** прогресс-бар загрузки реализовать через `XMLHttpRequest`, а не `fetch` — единственное обоснованное исключение из fetch-паттерна, принятого в остальном фронтенде; задокументировать это решение в `apps/web/CLAUDE.md` при реализации.
5. **Инфраструктура:** добавить директорию загрузок в `.gitignore`; директорию загрузок **не** монтировать как статические файлы Express — единственный доступ к содержимому файла должен идти через защищённую ручку скачивания.
