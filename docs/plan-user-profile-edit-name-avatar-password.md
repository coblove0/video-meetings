# Plan: Профиль пользователя — редактирование имени, загрузка аватара, смена пароля

**PRD:** docs/prd-user-profile-edit-name-avatar-password.md
**Ресерч:** docs/research-user-profile-edit-name-avatar-password.md
**Дата:** 2026-07-31

## Архитектурные решения (по итогам анализа кода и ресерча)

- Все новые use case'ы — по CQRS-паттерну проекта: `impl/*.command.ts` / `impl/*.query.ts` + `handlers/*.handler.ts`, никаких сервисов. Диспатч через `CommandBus`/`QueryBus` из тонкого контроллера.
- В `users`-модуле сейчас нет контроллера (только внутренние command/query handlers). Добавляем `UsersController` в этот же модуль, `@UseGuards(JwtAuthGuard)`, `imports: [CqrsModule, AuthModule]` — по образцу `meeting-files.module.ts`. Цикла зависимостей не возникает: `AuthModule` не импортирует `UsersModule`, а общается с ним только через шины.
- Все эндпоинты профиля работают только с `@CurrentUser() user: AuthenticatedUser` (`userId` из JWT) — id никогда не принимается из параметров запроса, поэтому чтение/изменение чужого профиля архитектурно невозможно (закрывает критерий готовности про доступ к чужому профилю).
- Одна миграция Prisma добавляет сразу три поля на `User`: `name String?`, `avatarPath String?`, `avatarMimeType String?`. Третье поле нужно, чтобы при отдаче аватара было чем заполнить `Content-Type` (в `MeetingFilesController.download()` он берётся из колонки `mimeType`) — вносим его сразу, чтобы не делать вторую миграцию в фазе 3.
- Оба handler'а профиля читают пользователя явным `select: { id, email, name, avatarPath }` и возвращают наружу `{ id, email, name, hasAvatar }` — `passwordHash` и путь на диске клиенту не уходят. Одинаковая форма ответа у `GET` и `PATCH` позволяет фронтенду обновлять состояние ответом `PATCH` без второго запроса.
- `UpdateProfileDto` — обычный класс с `class-validator` (`@IsString() @MaxLength(100)` + `@Transform` с `trim`), без `@nestjs/mapped-types`/`PartialType`: этой зависимости в проекте нет и ставить её ради одного поля не нужно. Пустая строка после trim трактуется как сброс имени в `null`. Лишние поля в теле отсекает глобальный `ValidationPipe` (`whitelist`/`forbidNonWhitelisted`).
- Аватар хранится как файл на диске по тому же принципу, что `MeetingFile` (`randomUUID()`, `diskStorage`, `fileFilter` по MIME, `limits.fileSize`), но в отдельной поддиректории `uploads/avatars` и с отдельными более строгими константами (`AVATAR_MAX_FILE_SIZE_BYTES = 5MB`, `ALLOWED_AVATAR_MIME_TYPES = image/jpeg, image/png`) в новом `avatar-multer.config.ts`. Расширение файла на диске выводится из MIME-типа (`image/jpeg → .jpg`), а не из `originalname` — пользовательский ввод в имя файла не попадает вообще.
- 415 (не тот тип) и 413 (превышен размер) реализовывать не нужно: `fileFilter` отдаёт `UnsupportedMediaTypeException`, а `LIMIT_FILE_SIZE` конвертируется в `PayloadTooLargeException` самим `@nestjs/platform-express`; multer при аборте по лимиту сам удаляет недописанный файл. В тестах эти коды всё равно проверяем.
- Поверх `fileFilter` (он проверяет только клиентский `Content-Type`) handler сверяет первые байты записанного файла с сигнатурами JPEG (`FF D8 FF`) и PNG (`89 50 4E 47 0D 0A 1A 0A`); при несовпадении файл удаляется и бросается `UnsupportedMediaTypeException`. Библиотека `file-type` не используется — с v17 она ESM-only, а `apps/api` собирается в CommonJS.
- Один файл на пользователя, без таблицы истории. Порядок замены: прочитать текущий `avatarPath` → записать новый путь и MIME в БД → только потом `unlink(oldPath).catch(() => undefined)`. Если пользователь не найден — удалить только что загруженный файл и бросить 404 (как в `UploadMeetingFileHandler`).
- Аватар отдаётся только через авторизованный эндпоинт `GET /users/me/avatar` (стриминг файла), а не статической раздачей — в проекте нет публичных профилей и нет кук, весь auth только через `Authorization: Bearer`. Заголовки: `Content-Type` из `avatarMimeType`, `Content-Disposition: inline`, `X-Content-Type-Options: nosniff`, `Cache-Control: private, max-age=0, must-revalidate`. Фронтенд получает картинку через `fetch` + `URL.createObjectURL`, а не через `<img src>` напрямую (иначе заголовок не уйдёт).
- Разделение ответственности между `GetAvatarQuery`-handler'ом и контроллером — по образцу `download-meeting-file`: **handler** только находит пользователя и проверяет, что `avatarPath` заполнен (`NotFoundException`, если аватара нет), возвращает путь и MIME — без `fs`/HTTP-специфики; сборка `StreamableFile`, `createReadStream` и заголовков — в `UsersController`. Перед созданием стрима контроллер делает `stat()` и превращает `ENOENT` в честный 404, иначе при расхождении БД и диска клиент получит оборванный ответ уже после отправки заголовков.
- Смена пароля переиспользует `bcrypt` напрямую (`SALT_ROUNDS = 10`, как в `register.handler.ts` — одно значение на оба места, не заводим второй cost) и то же правило валидации нового пароля, что в `RegisterDto` (`@IsString() @MinLength(8)`), плюс `@MaxLength(72)`: bcrypt молча игнорирует всё после 72 байт.
- Неверный текущий пароль → `BadRequestException` (400), **не** 401. Весь фронтенд трактует 401 как «сессия истекла» и редиректит на `/auth/login`, то есть 401 разлогинил бы пользователя из-за обычной опечатки. Утечки информации нет: вызов уже аутентифицирован.
- Ранее выданные JWT переживают смену пароля (нет revocation-списка и `tokenVersion`) — по PRD разлогинивание других сессий вне скоупа; фиксируем это как осознанное ограничение в `apps/api/CLAUDE.md`.
- Фронтенд: новая страница `/profile`, копирует существующий паттерн — клиентская проверка `localStorage.getItem('accessToken')` в `useEffect` с редиректом на `/auth/login` (без middleware/контекста), HeroUI-компоненты (заглушка аватара — готовый `Avatar` / `Avatar.Fallback` из HeroUI v3, не своя вёрстка), `fetch`/`XMLHttpRequest` напрямую к API (без общего клиента), загрузка файла через `XMLHttpRequest` с `onprogress` — по образцу формы загрузки файла встречи. Blob URL аватара revoke'ается в cleanup'е `useEffect`/при замене, а не сразу после присвоения `src`.

## TDD-подход (уровень всего приложения)

Это общий принцип разработки для репозитория в целом (`apps/api` и `apps/web` одинаково), а не только для этой фичи — цикл **Red → Green → Refactor**:

1. **Red** — сначала пишется тест на ещё не реализованное поведение, и явно проверяется, что он падает. В `apps/api` это unit-тест handler'а/DTO (mock `PrismaService`, по образцу `upload-meeting-file.handler.spec.ts`) и/или e2e-тест эндпоинта (`test/*.e2e-spec.ts`). В `apps/web` отдельного unit-раннера для React-компонентов в проекте нет — там red-тестом выступает Playwright e2e (`apps/web/e2e/*.spec.ts`), написанный до страницы/формы.
2. **Green** — пишется минимальная реализация, достаточная, чтобы тест прошёл, без забегания вперёд по функциональности, которая ещё не покрыта тестом.
3. **Refactor** — при зелёных тестах код приводится к конвенциям проекта (CQRS-паттерн `impl/`+`handlers/`, вынесение констант в `*.config.ts` и т.д.); тесты остаются зелёными на всём протяжении рефакторинга.

Внутри каждой фазы плана ниже это выражено порядком задач: тест — первым пунктом списка (red), реализация — следующим (green). Порядок задач в фазе — это и есть порядок выполнения, и это же правило должно применяться к будущим фичам за пределами этого плана, а не только к профилю пользователя.

Исключение — миграция Prisma в Фазе 1: она идёт до тестов, так как без неё нет TS-типов (`user.name`, `user.avatarPath`, `user.avatarMimeType`) для написания даже unit-тестов на mock `PrismaService`.

## Фазы реализации

### Фаза 1: Backend — миграция и просмотр/редактирование имени

**Цель:** Минимальный рабочий путь (tracer bullet, backend-часть): в БД появляются поля профиля, есть защищённое JWT API для чтения текущего профиля и изменения имени.
**Затрагивает:** database, backend
**Задачи:**

- [ ] Prisma-миграция: добавить `name String?`, `avatarPath String?` и `avatarMimeType String?` в модель `User` одной миграцией (нужна для типов до написания тестов)
- [ ] Написать unit-тесты (red) для `GetCurrentUserQuery` и `UpdateProfileCommand` handler'ов: happy path, обрезка пробелов в имени, пустая строка → `null`, отсутствие `passwordHash` в результате — handler'ов ещё нет
- [ ] Реализовать оба handler'а до прохождения unit-тестов (green): явный `select`, ответ `{ id, email, name, hasAvatar }`, `UpdateProfileCommand` обновляет `name` только для `userId` из JWT
- [ ] Написать e2e-тест (red) `users.e2e-spec.ts`: `GET`/`PATCH /users/me` → 200 для валидного имени, 401 без токена, 400 на лишнее поле в теле и на имя длиннее 100 символов, персистентность имени после повторного `GET` — контроллера ещё нет
- [ ] Реализовать `UpdateProfileDto` и `UsersController` под `JwtAuthGuard` (`UsersModule` импортирует `AuthModule`) до прохождения e2e-теста (green)

**Когда готова:** `GET /users/me` и `PATCH /users/me` работают через curl/e2e с валидным JWT и возвращают только `{ id, email, name, hasAvatar }`; без токена — 401; неаутентифицированный запрос и запрос к чужому профилю архитектурно невозможны.

### Фаза 2: Frontend — страница профиля (просмотр и имя)

**Цель:** Пользователь может открыть `/profile`, увидеть имя/заглушку аватара/email и изменить имя — завершает tracer bullet.
**Затрагивает:** frontend
**Задачи:**

- [ ] Написать Playwright e2e (red) `profile-page.spec.ts`: сидирование пользователя через API, открытие `/profile`, проверка отображения email/имени, изменение имени и проверка после `reload()`, редирект неаутентифицированного на `/auth/login` — страницы ещё нет
- [ ] Реализовать страницу `apps/web/src/app/profile/page.tsx`: guard по `accessToken` из `localStorage`, загрузка данных через `GET /users/me`, отображение email (read-only), имени и заглушки аватара через HeroUI `Avatar`/`Avatar.Fallback` с инициалами (сам аватар подключается в фазе 4)
- [ ] Форма редактирования имени (HeroUI `Form`/`TextField`), сохранение через `PATCH /users/me`, обновление отображаемого значения ответом `PATCH` без перезагрузки страницы
- [ ] Обработка ошибок API (401 → очистка токена и редирект на логин, прочие → `Alert`), довести e2e-тест до зелёного
- [ ] Ссылка на `/profile` в шапке главной страницы (HeroUI `Avatar` + имя), данные о текущем пользователе брать из `GET /users/me` вместо ручного `atob`-разбора JWT — иначе страница профиля недостижима из UI

**Когда готова:** в браузере аутентифицированный пользователь попадает на профиль по ссылке из шапки, видит и меняет имя, изменение переживает обновление страницы; неаутентифицированный переход на `/profile` ведёт на страницу логина.

### Фаза 3: Backend — загрузка и замена аватара

**Цель:** Пользователь может загрузить/заменить аватар через API с валидацией типа и размера.
**Затрагивает:** backend, database (использование полей из фазы 1)
**Задачи:**

- [ ] Написать unit-тесты (red) для `UploadAvatarCommand`/handler и `GetAvatarQuery`/handler: успешная загрузка, замена (запись в БД до `unlink` старого файла), отказ по несовпадению магических байт с удалением файла, аватар не найден — handler'ов ещё нет
- [ ] Написать e2e-тесты (red) `avatar.e2e-spec.ts`: успешная загрузка JPG/PNG ≤5MB (буферы с настоящими магическими байтами), 415 для не-изображения, 413 для файла >5MB (аватар не меняется), повторная загрузка заменяет файл на диске; пути загруженных файлов чистятся в `afterAll` — эндпоинтов ещё нет
- [ ] `avatar-multer.config.ts`: `diskStorage` в `AVATAR_UPLOAD_DIR` (по умолчанию `./uploads/avatars`, создаётся при импорте), имя файла `randomUUID()` + расширение из MIME-типа, `limits.fileSize = 5MB`, `fileFilter` только `image/jpeg`/`image/png`
- [ ] Реализовать `UploadAvatarCommand`/handler и `GetAvatarQuery`/handler до прохождения unit-тестов (green): проверка магических байт с удалением файла при отказе, запись `avatarPath`/`avatarMimeType` в БД и последующий `unlink` старого файла; `GetAvatarQuery`-handler возвращает только путь и MIME (без `fs`/`StreamableFile`)
- [ ] Реализовать `POST /users/me/avatar` (`FileInterceptor('file', avatarMulterOptions)`, `BadRequestException` без файла) и `GET /users/me/avatar` (`stat()` → `StreamableFile`, заголовки `Content-Type`/`inline`/`nosniff`/`Cache-Control: private`, 404 если аватар не загружен или файла нет на диске) в `UsersController` до прохождения e2e-тестов (green)

**Когда готова:** через API можно загрузить, заменить и скачать аватар; невалидные файлы (по MIME и по содержимому) отклоняются с понятной ошибкой и не меняют текущий аватар; на диске не остаётся файлов от предыдущих аватаров.

### Фаза 4: Frontend — загрузка аватара в UI

**Цель:** Пользователь загружает аватар через страницу профиля и видит его вместо заглушки.
**Затрагивает:** frontend
**Задачи:**

- [ ] Написать Playwright e2e (red): загрузка валидного JPG и проверка, что картинка реально отрисовалась (`naturalWidth > 0`, а не по `src` — там будет `blob:`), попытка загрузки не-изображения/большого файла и проверка сообщения об ошибке — блока загрузки ещё нет
- [ ] Блок загрузки аватара на `/profile`: `Input type="file"` с предвалидацией типа и размера на клиенте до отправки, отправка через `XMLHttpRequest` с `FormData` (по образцу формы загрузки файла встречи), `ProgressBar` во время загрузки
- [ ] Отображение текущего аватара: `fetch('/users/me/avatar')` с `Authorization` → `URL.createObjectURL(blob)` в `Avatar.Image`, revoke в cleanup'е эффекта/при замене; `Avatar.Fallback` с инициалами, если аватар не загружен (404)
- [ ] Обработка ошибок загрузки: понятные сообщения для 415 (не изображение) и 413 (превышен размер), аватар на экране не меняется при ошибке
- [ ] Обновление отображаемого аватара сразу после успешной загрузки без перезагрузки страницы (новый blob URL, старый revoke'ается) — включая аватар в шапке главной страницы; довести e2e-тест до зелёного

**Когда готова:** в браузере пользователь загружает JPG/PNG до 5MB и видит его как аватар на странице профиля и в шапке; невалидные файлы дают понятную ошибку в UI без изменения текущего аватара; повторная загрузка визуально заменяет предыдущий аватар.

### Фаза 5: Backend — смена пароля

**Цель:** Пользователь может сменить пароль через API, зная текущий пароль.
**Затрагивает:** backend
**Задачи:**

- [ ] Написать unit-тесты (red) для `ChangePasswordCommand`/handler: верный текущий пароль → успех и хеш меняется, неверный → `BadRequestException` и хеш не меняется — handler'а ещё нет
- [ ] Написать e2e-тест (red): смена с верным текущим паролем → логин по старому не проходит, по новому проходит; смена с неверным текущим → 400, логин по старому по-прежнему работает — эндпоинта ещё нет
- [ ] `ChangePasswordDto`: `currentPassword: @IsString()`, `newPassword: @IsString() @MinLength(8) @MaxLength(72)`; тот же `@MaxLength(72)` добавить в `RegisterDto` (bcrypt игнорирует всё после 72 байт)
- [ ] Реализовать `ChangePasswordCommand`/handler (`bcrypt.compare` текущего, `bcrypt.hash` нового с тем же `SALT_ROUNDS`, что в `register.handler.ts`; 400 при неверном текущем пароле) до прохождения unit-тестов (green)
- [ ] Эндпоинт `POST /users/me/password` в `UsersController` под `JwtAuthGuard` до прохождения e2e-теста (green)

**Когда готова:** `POST /users/me/password` меняет пароль только при верном текущем пароле; после смены вход возможен только по новому паролю; неверный текущий пароль не меняет ничего и возвращает 400 с понятной ошибкой.

### Фаза 6: Frontend — форма смены пароля

**Цель:** Пользователь меняет пароль со страницы профиля.
**Затрагивает:** frontend
**Задачи:**

- [ ] Написать Playwright e2e (red): смена пароля через UI с последующим логином по новому паролю; попытка с неверным текущим паролем показывает ошибку в форме и оставляет пользователя на `/profile` — формы ещё нет
- [ ] Форма смены пароля на `/profile` (HeroUI): поля «текущий пароль» и «новый пароль» с `autoComplete="current-password"`/`"new-password"` и show/hide-кнопкой как на странице логина, клиентская валидация длины нового пароля
- [ ] Отправка через `POST /users/me/password`, индикация успеха (`Alert`), очистка полей после успешной смены
- [ ] Обработка 400 «неверный текущий пароль» локально в форме (не наследовать общее правило «401 → редирект на логин»), поля не сбрасываются молча; довести e2e-тест до зелёного

**Когда готова:** пользователь меняет пароль через UI, при следующем логине работает только новый пароль; неверный текущий пароль даёт понятную ошибку в форме и не разлогинивает пользователя.
