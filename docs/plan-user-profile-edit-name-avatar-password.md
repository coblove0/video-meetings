# Plan: Профиль пользователя — редактирование имени, загрузка аватара, смена пароля

**PRD:** docs/prd-user-profile-edit-name-avatar-password.md
**Дата:** 2026-07-31

## Архитектурные решения (по итогам анализа кода)

- Все новые use case'ы — по CQRS-паттерну проекта: `impl/*.command.ts` / `impl/*.query.ts` + `handlers/*.handler.ts`, никаких сервисов. Диспатч через `CommandBus`/`QueryBus` из тонкого контроллера.
- В `users`-модуле сейчас нет контроллера (только внутренние command/query handlers). Добавляем `UsersController` в этот же модуль, `@UseGuards(JwtAuthGuard)`, `imports: [AuthModule, CqrsModule]` — по образцу `meeting-files.module.ts`.
- Все эндпоинты профиля работают только с `@CurrentUser() user: AuthenticatedUser` (`userId` из JWT) — id никогда не принимается из параметров запроса, поэтому чтение/изменение чужого профиля архитектурно невозможно (закрывает критерий готовности про доступ к чужому профилю).
- Одна миграция Prisma добавляет оба новых поля на `User` сразу (`name String?`, `avatarPath String?`), даже если `avatarPath` не используется до фазы 3 — избегаем двух миграций подряд.
- Аватар хранится как файл на диске по тому же принципу, что `MeetingFile` (`randomUUID()` + расширение, `diskStorage`, `fileFilter` по MIME, `limits.fileSize`), но с отдельными более строгими константами (`AVATAR_MAX_FILE_SIZE_BYTES = 5MB`, `ALLOWED_AVATAR_MIME_TYPES = image/jpeg, image/png`) в новом `avatar-multer.config.ts`. Один файл на пользователя, без отдельной таблицы истории — при перезаписи старый файл удаляется через `unlink().catch(() => undefined)` (как в `DeleteMeetingFileHandler`).
- Аватар отдаётся только через авторизованный эндпоинт `GET /users/me/avatar` (стриминг файла, как `download-meeting-file`), а не статической раздачей — в проекте нет публичных профилей и нет кук, весь auth только через `Authorization: Bearer`. Фронтенд получает картинку через `fetch` + `URL.createObjectURL`, а не через `<img src>` напрямую (иначе заголовок не уйдёт).
- Смена пароля переиспользует `bcrypt` напрямую (`SALT_ROUNDS = 10`, как в `register.handler.ts`) и то же правило валидации нового пароля, что в `RegisterDto` (`@IsString() @MinLength(8)`).
- Фронтенд: новая страница `/profile`, копирует существующий паттерн — клиентская проверка `localStorage.getItem('accessToken')` в `useEffect` с редиректом на `/auth/login` (без middleware/контекста), HeroUI-компоненты, `fetch`/`XMLHttpRequest` напрямую к API (без общего клиента), загрузка файла через `XMLHttpRequest` с `onprogress` — по образцу формы загрузки файла встречи.

## TDD-подход (уровень всего приложения)

Это общий принцип разработки для репозитория в целом (`apps/api` и `apps/web` одинаково), а не только для этой фичи — цикл **Red → Green → Refactor**:

1. **Red** — сначала пишется тест на ещё не реализованное поведение, и явно проверяется, что он падает. В `apps/api` это unit-тест handler'а/DTO (mock `PrismaService`, по образцу `upload-meeting-file.handler.spec.ts`) и/или e2e-тест эндпоинта (`test/*.e2e-spec.ts`). В `apps/web` отдельного unit-раннера для React-компонентов в проекте нет — там red-тестом выступает Playwright e2e (`apps/web/e2e/*.spec.ts`), написанный до страницы/формы.
2. **Green** — пишется минимальная реализация, достаточная, чтобы тест прошёл, без забегания вперёд по функциональности, которая ещё не покрыта тестом.
3. **Refactor** — при зелёных тестах код приводится к конвенциям проекта (CQRS-паттерн `impl/`+`handlers/`, вынесение констант в `*.config.ts` и т.д.); тесты остаются зелёными на всём протяжении рефакторинга.

Внутри каждой фазы плана ниже это выражено порядком задач: тест — первым пунктом списка (red), реализация — следующим (green). Порядок задач в фазе — это и есть порядок выполнения, и это же правило должно применяться к будущим фичам за пределами этого плана, а не только к профилю пользователя.

Исключение — миграция Prisma в Фазе 1: она идёт до тестов, так как без неё нет TS-типов (`user.name`, `user.avatarPath`) для написания даже unit-тестов на mock `PrismaService`.

## Фазы реализации

### Фаза 1: Backend — миграция и просмотр/редактирование имени

**Цель:** Минимальный рабочий путь (tracer bullet, backend-часть): в БД появляются поля профиля, есть защищённое JWT API для чтения текущего профиля и изменения имени.
**Затрагивает:** database, backend
**Задачи:**

- [ ] Prisma-миграция: добавить `name String?` и `avatarPath String?` в модель `User` (нужна для типов до написания тестов)
- [ ] Написать unit-тесты (red) для `GetCurrentUserQuery` и `UpdateProfileCommand` handler'ов — happy path + edge case, handler'ов ещё нет
- [ ] Реализовать оба handler'а до прохождения unit-тестов (green): `GetCurrentUserQuery` возвращает `{ id, email, name, hasAvatar }`, `UpdateProfileCommand` обновляет `name` только для `userId` из JWT
- [ ] Написать e2e-тест (red) `users.e2e-spec.ts`: 200 для валидного имени через `GET`/`PATCH /users/me`, 401 без токена, персистентность имени после повторного `GET` — контроллера ещё нет
- [ ] Реализовать `UsersController` под `JwtAuthGuard` (`UsersModule` импортирует `AuthModule`) до прохождения e2e-теста (green)

**Когда готова:** `GET /users/me` и `PATCH /users/me` работают через curl/e2e с валидным JWT; без токена — 401; неаутентифицированный запрос и запрос к чужому профилю архитектурно невозможны.

### Фаза 2: Frontend — страница профиля (просмотр и имя)

**Цель:** Пользователь может открыть `/profile`, увидеть имя/заглушку аватара/email и изменить имя — завершает tracer bullet.
**Затрагивает:** frontend
**Задачи:**

- [ ] Написать Playwright e2e (red) `profile-page.spec.ts`: сидирование пользователя через API, открытие `/profile`, проверка отображения email/имени, изменение имени и проверка после `reload()` — страницы ещё нет
- [ ] Реализовать страницу `apps/web/src/app/profile/page.tsx`: guard по `accessToken` из `localStorage` (редирект на `/auth/login`), загрузка данных через `GET /users/me`
- [ ] Отображение email (read-only), имени, заглушки аватара (аватар из фазы 3 ещё не подключаем)
- [ ] Форма редактирования имени (HeroUI `Form`/`TextField`), сохранение через `PATCH /users/me`, обновление отображаемого значения без перезагрузки страницы
- [ ] Обработка ошибок API (401 → редирект на логин, прочие → `Alert`), довести e2e-тест до зелёного

**Когда готова:** в браузере аутентифицированный пользователь видит и меняет имя, изменение переживает обновление страницы; неаутентифицированный переход на `/profile` ведёт на страницу логина.

### Фаза 3: Backend — загрузка и замена аватара

**Цель:** Пользователь может загрузить/заменить аватар через API с валидацией типа и размера.
**Затрагивает:** backend, database (использование поля из фазы 1)
**Задачи:**

- [ ] Написать unit-тесты (red) для `UploadAvatarCommand`/handler и `GetAvatarQuery`/handler: успешная загрузка, замена с удалением старого файла, аватар не найден — handler'ов ещё нет
- [ ] Написать e2e-тесты (red) (`avatar.e2e-spec.ts`): успешная загрузка JPG/PNG ≤5MB, 415 для не-изображения, 413 для файла >5MB (аватар не меняется), повторная загрузка заменяет файл на диске — эндпоинтов ещё нет
- [ ] `avatar-multer.config.ts`: `diskStorage` в `AVATAR_UPLOAD_DIR` (можно = `UPLOAD_DIR`), имя файла `randomUUID()+ext`, `limits.fileSize = 5MB`, `fileFilter` только `image/jpeg`/`image/png` (415 при отказе)
- [ ] Реализовать `UploadAvatarCommand`/handler и `GetAvatarQuery`/handler до прохождения unit-тестов (green)
- [ ] Реализовать `POST /users/me/avatar` (`FileInterceptor('file', avatarMulterOptions)`, `BadRequestException` без файла) и `GET /users/me/avatar` (`StreamableFile`, 404 если не загружен) в `UsersController` до прохождения e2e-тестов (green)

**Когда готова:** через API можно загрузить, заменить и скачать аватар; невалидные файлы отклоняются с понятной ошибкой и не меняют текущий аватар; на диске не остаётся файлов от предыдущих аватаров.

### Фаза 4: Frontend — загрузка аватара в UI

**Цель:** Пользователь загружает аватар через страницу профиля и видит его вместо заглушки.
**Затрагивает:** frontend
**Задачи:**

- [ ] Написать Playwright e2e (red): загрузка валидного JPG и проверка отображения, попытка загрузки не-изображения/большого файла и проверка сообщения об ошибке — блока загрузки ещё нет
- [ ] Блок загрузки аватара на `/profile`: `Input type="file"`, отправка через `XMLHttpRequest` с `FormData` (по образцу формы загрузки файла встречи), `ProgressBar` во время загрузки
- [ ] Отображение текущего аватара: `fetch('/users/me/avatar')` с `Authorization`, `URL.createObjectURL(blob)` в `<img>`; заглушка, если аватар не загружен (404)
- [ ] Обработка ошибок загрузки: понятные сообщения для 415 (не изображение) и 413 (превышен размер), аватар на экране не меняется при ошибке
- [ ] Обновление отображаемого аватара сразу после успешной загрузки без перезагрузки страницы, довести e2e-тест до зелёного

**Когда готова:** в браузере пользователь загружает JPG/PNG до 5MB и видит его как аватар; невалидные файлы дают понятную ошибку в UI без изменения текущего аватара; повторная загрузка визуально заменяет предыдущий аватар.

### Фаза 5: Backend — смена пароля

**Цель:** Пользователь может сменить пароль через API, зная текущий пароль.
**Затрагивает:** backend
**Задачи:**

- [ ] Написать unit-тесты (red) для `ChangePasswordCommand`/handler: верный текущий пароль → успех и хеш меняется, неверный → ошибка и хеш не меняется — handler'а ещё нет
- [ ] Написать e2e-тест (red): смена с верным текущим паролем → логин по старому не проходит, по новому проходит; смена с неверным текущим → ошибка, логин по старому по-прежнему работает — эндпоинта ещё нет
- [ ] `ChangePasswordDto`: `currentPassword: string`, `newPassword: @IsString() @MinLength(8)` (те же правила, что `RegisterDto`)
- [ ] Реализовать `ChangePasswordCommand`/handler (`bcrypt.compare` текущего, `bcrypt.hash` нового) до прохождения unit-тестов (green)
- [ ] Эндпоинт `POST /users/me/password` в `UsersController` под `JwtAuthGuard` до прохождения e2e-теста (green)

**Когда готова:** `POST /users/me/password` меняет пароль только при верном текущем пароле; после смены вход возможен только по новому паролю; неверный текущий пароль не меняет ничего и возвращает понятную ошибку.

### Фаза 6: Frontend — форма смены пароля

**Цель:** Пользователь меняет пароль со страницы профиля.
**Затрагивает:** frontend
**Задачи:**

- [ ] Написать Playwright e2e (red): смена пароля через UI с последующим логином по новому паролю; попытка с неверным текущим паролем показывает ошибку и не разлогинивает пользователя — формы ещё нет
- [ ] Форма смены пароля на `/profile` (HeroUI): поля «текущий пароль», «новый пароль», клиентская валидация длины нового пароля
- [ ] Отправка через `POST /users/me/password`, индикация успеха (`Alert`), очистка полей после успешной смены
- [ ] Обработка ошибки неверного текущего пароля — понятное сообщение, поля не сбрасываются молча; довести e2e-тест до зелёного

**Когда готова:** пользователь меняет пароль через UI, при следующем логине работает только новый пароль; неверный текущий пароль даёт понятную ошибку в форме.
